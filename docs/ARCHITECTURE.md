## 2. Architecture and common invariants

Use a modular monolith with a bilingual same-origin browser UI/API, PostgreSQL as financial/revision/policy/job authority, protected local source storage, and independently scheduled parser/OCR, retrieval/generation and forecast workers. Exact structured retrieval and deterministic calculations precede language generation. Local model/OCR adapters are interchangeable and pinned; no automatic cloud/provider fallback, outbound tool network, paid service or operational Lightning dependency.

Browser → loopback HTTPS UI/API → authenticated authorization broker → transaction-scoped DB/tool access → protected source service. DB and model gateway are loopback/internal only, never browser-direct. Parser/model processes receive bounded job inputs, no login/owner credentials, and no general filesystem/network authority. Backup/restore and schema administration are offline maintenance boundaries (§3, §7).

Each request acquires one database-consistent snapshot transaction to select an immutable manifest of fact/document, calendar, FX, budget, mapping, consolidation, formula, rounding and index revisions. All tools resolve that manifest. Authorization is **current**, independent of historical selection. Complete transitive lineage includes source documents, OCR decisions, mappings, rates, budgets, eliminations, formulas and model/data manifests. Unknown lineage denies protected delivery. Cache reuse requires complete current dependency authorization for the receiving actor; tenant-wide ACL revision is insufficient.

Publication: stage immutable verified blobs; atomically commit authoritative fact revision/effective pointer, audit, dependent stale watermark and durable outbox; finalize blob/index readiness asynchronously. A committed pointer to unfinalized/missing evidence stays unavailable. Every effective change invalidates current dependents immediately through the watermark, even before outbox delivery. Idempotent events use tenant/event/generation identity. Worker publish requires current input fingerprint, valid lease/fence, sufficient generation and current rights in a serialized transaction. Historical stale results may be served only explicitly labeled and currently authorized. Cancellation, expired workers and obsolete manifests cannot publish current results.

Protected effect manifests bind tenant, requester, exact intent digest, target/input/policy versions, approvers and expiry. Low-risk literal extraction confirmation requires an independent authorized reviewer; it grants extraction verification only. Source authority, financial-method approval, effective corrections, restatements, ACL grants, deletion, FX/consolidation/rounding policy changes and releases are conservatively high-impact: two distinct currently authorized human approvers, neither the proposer. Unclassified actions remain pending. All requester/approver/delegate/source rights, intent, expiry and versions are checked atomically with once-only consumption/effect. No numeric materiality exception bypasses dual control. A solo operator cannot provide real two-person approval; simulated identities test mechanics only.

Common statuses travel with every value, report, cache and explanation: `SOURCE_VERIFIED_ONLY` (literal extraction checked), `PRELIMINARY`, `SUPPORTED_CERTIFIED` (eligible reviewed analytical method and approved inputs, never statutory certification), `INCOMPLETE` (missing evidence), `UNSUPPORTED_METHOD` (unreviewed/outside method domain), `CONFLICT`, `RESTRICTED`, `STALE`, `UNANSWERABLE`. Forbidden access is handled first with a nonrevealing response; subsequent checks distinguish conflicts, unsupported methods and missing evidence. Missing is never zero. A correct arithmetic result alone grants no financial status.

## 3. B1 — tenant, document and privileged-path enforcement

### 3.1 Logical roles and GRANT ceiling

This is a **complete logical inventory for the proposed pilot**, not a claim of existing tables or executable GRANTs. Every implementation object must map to one class below, and every actual function/view/trigger/worker/credential must be listed by qualified name, owner, caller, operation and policy at V0. Unclassified or newly privileged paths receive no runtime grant and remain blocked until reviewed into this inventory. Application Viewer/Analyst/Admin roles are policy data, never DB owner roles.

| DB identity | Allowed grants / purpose | Explicitly denied |
|---|---|---|
| `schema_owner` (NOLOGIN) | Own schemas/tables, policies; reachable only by offline `migrator` | Runtime membership, browser/worker use |
| `migrator` (offline LOGIN) | SET ROLE schema_owner for reviewed DDL in closed maintenance | App secret store, concurrent live service use |

All runtime LOGINS also NOSUPERUSER/NOCREATEDB/NOCREATEROLE/NOREPLICATION; no role memberships permitting SET ROLE into privileged identities. Revoke PUBLIC CONNECT except explicitly used logins, PUBLIC schema CREATE, PUBLIC table/sequence/function privileges; restrict TEMP to none for runtime. Default privileges grant nothing. No runtime TRUNCATE, REFERENCES, trigger creation, extensions, COPY-to-file/program, server-file/program roles, ownership, replication/large-object access or SECURITY DEFINER creation. COPY/read/query access is limited to already authorized relations, with no raw SQL tool. Only exact needed sequence USAGE is granted to an executor when a listed procedure requires it. DB credentials are OS-account restricted and isolated from parser/model files. PostgreSQL superusers and BYPASSRLS escape RLS; table owners require FORCE to be subject to it. Whole-table and referential checks need separate restrictions. These distinctions underpin this proposed ceiling. [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html)

### 3.2 Relation, view, function and non-DB path matrix

Every tenant **data** table, including partitions and history/staging tables, has ENABLE and FORCE RLS, explicit command policies, and tenant-scoped keys/FKs `(tenant_id, object_id)`. Runtime cannot query partitions directly. Required RLS predicate is the conjunction of a valid context, matching tenant, current active account/session/membership, required action role, no deletion, and current document/dependency entitlement. It is a restrictive boundary so a later permissive policy cannot OR it away. INSERT/UPDATE WITH CHECK enforces the same boundary on new rows, forbids moving tenant/document identity and binds the full input manifest. Effective writes use procedures only. Empty/malformed/expired context is false, never a default tenant. ACL metadata helpers return booleans without exposing protected names or granting content rights.

Private control tables (credentials, sessions, context bindings, membership/document grants and safety ledger metadata) have ENABLE/FORCE too, but a separate nonrecursive control-plane policy: only auth_owner's exact bootstrap/context functions, policy_reader read-only boolean helpers, and scope-validated effect/lifecycle procedures may access their minimum columns. These NOLOGIN identities are granted explicit command policies and column privileges, never a runtime role membership. They do not call the data RLS context helper recursively to establish that same context. Bootstrap verifies the credential/session before looking up its authorized memberships, never returns arbitrary account/tenant enumeration. Grant/revoke/deletion procedures enforce the already valid context and approved action manifest before private metadata mutation. Neither app_api nor job_runner nor auth_gateway can read or alter a private control relation directly; auth_owner and policy_reader have no financial-table SELECT grants. Effect/lifecycle executors retain only their inventoried data operations under FORCE RLS, with no generic content-returning procedure. This explicitly inventoried metadata exception does not waive data-table RLS. An audit_reader uses a custodian-issued context bound to its real identity, tenant and audit-only grant; it cannot mint its own context or use financial tools.

### 3.3 Trusted context, pools, workers and revocation

Do not authorize from writable session variables such as `app.tenant_id`. The trusted auth gateway verifies the opaque browser session, current account epoch/membership and selected tenant, then issues a random single-use capability (proposed 256 bits, ≤30 seconds to activate), stored hashed in a private registry. It binds actor, session/epoch, tenant, action ceiling, request or job ID, manifest, expiry and expected runtime DB identity. No client/LLM supplies authoritative actor or role. Runtime cannot insert or edit capabilities. Activation validates it and creates a private binding to **backend PID, transaction identity, database session_user and capability**, valid only in that transaction. RLS helpers consult this binding, not GUC text. A capability cannot bind to a second transaction/tenant. Login/auth broker credentials remain separate from app/job credentials; compromise of that trusted broker/OS is outside the runtime-only containment claim and requires revocation/recovery.

Pool checkout: rollback any transaction, reset session settings/role/prepared temporary state; if cleanup is uncertain discard the connection. BEGIN, activate capability, acquire data snapshot, perform scoped operations, then commit/rollback. Successful commit, exception, timeout and cancellation all end the binding; connection release must verify idle/reset state. An old private binding cannot match a new transaction. Never multiplex actors within one transaction or switch tenant mid-transaction. Each tool continuation obtains a fresh validated context; background jobs bind a DB-validated submitter, tenant, manifest, session/account epoch and narrowly scoped lease, never trust queue fields alone. Session expiry/revocation/switch cancels its privileged continuations; a new authenticated submission is required to resume.

Retention/purge work is distinct from user jobs: lifecycle_runner receives a one-tenant/one-plan capability for the authorized maintenance principal, bound to exact already-tombstoned IDs or elapsed fixed-policy TTLs. It may delete/record completion even after the original user's membership is revoked, but may not inspect/export content, certify facts, cancel tombstones or revive grants. Deletion authorization is consumed once and its durable plan is resumable; a different purge target requires a new validated plan. Grant the lifecycle_executor only necessary DELETE/metadata-update columns under plan-specific RLS. No all-tenant service capability is issued. The scheduler can read only opaque queue/expiry metadata through its listed claim function, never rows/filenames/candidate text without a scoped job context.

Use short transactions for protected reads; snapshot data selection is repeatable, but policy freshness is not taken from an old repeatable-read snapshot. Before each tool read and immediately before protected bytes/claims are released, a fresh authorization transaction checks current epoch/grants/tombstones. Serialize the final delivery or write check against revocation with a shared authorization-generation lock; revocation takes the exclusive lock and increments the generation. Delivery linearized before revocation may already have been seen; after revocation commits, no new protected delivery is allowed. Streaming sensitive output is buffered until verified, or each bounded chunk repeats the check. Already downloaded user-controlled copies cannot be recalled.

## 4. B4 — selected localhost browser authentication

Select **same-origin HTTPS on `https://localhost:8443` only**, served by a process bound exclusively to `127.0.0.1`. No HTTP listener, redirect, certificate-warning bypass, IP-origin alias, IPv6 alias, reverse proxy or tunnel. A locally provisioned certificate must have localhost SAN, a browser-trusted local issuer and an OS-restricted private key; certificate provisioning is future authorized work, not done here. Top-level GET may lack Origin but cannot mutate state. CORS grants none, cross-origin preflights denied, Fetch Metadata cross-site requests rejected, no embedding (`frame-ancestors 'none'`). Use an explicit CSP with local assets and no arbitrary HTML execution from sources. WebSocket is initially disabled; future use needs the same origin/session checks.

### 5.5 Reproducible pilot precision profile PP-01 (proposed)

Preserve exact source literals/decimals, scale, display increment and sign; normalize once. For pilot authoritative finite operations use arbitrary-precision decimal coefficients and exact integer/rational arithmetic, no binary float. Proposed ingestion domain: at most 34 significant coefficient digits, normalized fractional scale ≤18, absolute normalized input <10^24; approved direct rate >0 with scale ≤18. Exact intermediate addition/subtraction/multiplication uses up to 128 coefficient digits and scale ≤72; reject excessive scale/digits before silent truncation. Explicit profile-domain overflow → UNSUPPORTED_METHOD with a nonnumeric reason, never infinity/zero. Unknown/malformed source scale → PRELIMINARY/CONFLICT rather than fabricated precision.

Fixed formula order: normalize exact operands; resolve coverage/YTD in source currency; exact finite sums/products/subtractions; compute ratio as exact rational numerator/denominator (percent multiply numerator by 100); display from that rational with ROUND_HALF_EVEN at the final boundary. Record a 34-significant-digit decimal reference for divisions, with INEXACT flag when repeating; **do not use that rounded reference as a downstream operand**. This avoids double rounding and preserves 1/3 lineage. Final monetary display uses PP-01 approved pilot registry SAR=2, USD=2, EUR=2, JPY=0, KWD=3 decimal places (proposed presentation choices, not legal/accounting prescriptions); other currency display held until registry review. Percent display 2 decimal places, ratios in times 4 places. Imported facts retain their source display precision instead of asserting extra measured accuracy. Round once at final derived total; no line rounding unless a separately reviewed source-specific policy explicitly overrides PP-01. Version/profile and INEXACT/display-rounding flags follow exports.

Reconciliation uses exact normalized **source** values and exact residual, arithmetic tolerance zero. If a source independently rounds a value to increment q, with evidenced nearest-rounding convention, attach its interval ±q/2. For a linear equation, maximum source-display bound is sum of `abs(coefficient)*q/2`; more precise interval-intersection feasibility must also hold. Inside evidenced bound → `ROUNDING_CONSISTENT`, not exact reconciliation or invented hidden values. Unknown rounding convention/precision gives no presumed allowance. Derived FX/display rounding gets its own rational-vs-rendered residual and bound; never fold into source rounding. Financial materiality remains a specialist-approved escalation policy; until supplied all unexplained residuals require review and block reconciled status. Materiality cannot repair an equation or leave stale outputs current.

### 7.2 Backup scope, custody and failure handling

Proposed backup schedule: one encrypted consistent snapshot per 24 hours, target **RPO ≤24 elapsed hours**, target **RTO ≤8 elapsed hours** from declared recovery start, explicitly replacing the earlier unapproved one-business-day suggestion. Retention 7 days. These are proposals requiring owner acceptance and measured restore exercises; neither success nor disaster coverage is claimed now. RPO measured from incident to the newest fully verified recoverable snapshot, not job-start time. RTO ends only when service passes safety/integrity checks and can serve authorized requests. Deletion/revocation/effect-receipt safety ledger is synchronously checkpointed before acknowledging a protected effect; it cannot be lost within an ordinary financial-data RPO window.

Backup includes complete PostgreSQL physical snapshot plus required WAL through declared consistency point, raw evidence blobs and digests, fact/revision/effective pointers, dependencies, ACL/policy/membership/account epochs, budgets/FX/calendars/consolidation/formula/rounding versions, approvals/consumption records, durable jobs/outbox, managed reports/conversations still within retention, audit/checkpoints and tombstone/revocation ledger. Manifest declares DB consistency point, referenced blob digest inventory, ledger/audit head, config/schema/build/model registry IDs, format and key IDs. Rebuildable embeddings/indexes may be omitted and rebuilt; incompatible restored index cannot be served. No silently RLS-filtered tenant-only dump may be called a complete backup. Model binaries/licensed installers are separately reproducible pinned inputs, not assumed backed up. Sealed evaluation assets remain in custodian storage outside app backup.

Filesystem/DB consistency: choose a transaction-consistent DB snapshot; capture every blob referenced at that point while deletion/GC is fenced; validate digests and manifest. A complete ready backup includes a latest external safety-ledger checkpoint at/after that snapshot. Backup does not become READY until encryption, restore readability, reference closure and independent ledger/head checks succeed. Use standard authenticated encryption through a reviewed existing facility at implementation time; do not invent crypto.

Recovery coverage proposal is **local process/DB/file corruption with laptop and designated recovery media intact**. An encrypted recovery snapshot on the same laptop is insufficient for theft/total-machine loss. A separately custodied encrypted removable medium and separately protected key recovery copy may enable future machine-loss scope only after separately authorized setup and measured full recovery; no new purchase or cloud service is presumed. If the recovery medium/custodian is absent, mark recovery setup NOT READY, never claim advertised RPO/RTO. One physical operator does not establish independent organizational custody.

Key/audit custody: runtime account may unwrap only active source keys needed for authorized operations and append audit through a broker; backup encryption public key may be online, decryption private key and **daily audit-checkpoint** signing key are offline under designated custodian OS/account permissions. Store recovery key separately from encrypted media; tested recovery access, no secrets in Git/logs/backups in plaintext. Audit hash-chain records have signed daily checkpoints externally retained. A separate local safety-ledger broker runs under a designated custodian OS identity, with its own narrowly scoped online signing key inaccessible to app/parser/model accounts and an append-only recovery-medium journal. For grant/revoke/delete/approval consumption it synchronously durably records the signed monotonic event and head before success acknowledgment; the journal and latest head must survive corruption of the ordinary DB. Daily offline-signed anchors additionally detect journal rollback. No paid or network service is required, but the designated recovery medium must be available for protected writes. Runtime cannot alter/truncate audit or the external head. Verification detects change relative to the custodied trusted anchor; it does not promise tamper resistance against an OS administrator/custodian compromising all keys/media. Designated audit reader sees scoped minimal metadata only. Backup/restore privileges deliberately see all protected storage offline and are outside ordinary tenant runtime; their custody must be reviewed, not hidden as an RLS exception.

On backup failure/corruption: mark FAILED, retain last verified snapshot, record privacy-minimal reason and conspicuous local dashboard alert; no external messages authorized. Proposed retry after 15 minutes, maximum 3 attempts per schedule with bounded disk/memory; do not overwrite last good copy. If last verified backup age exceeds 24h or safety-ledger checkpoint is unavailable, recovery status DEGRADED; block financial approvals, destructive changes and writes requiring durability. Authorized safe reads may continue with local degraded banner; do not advertise RPO. A deletion request immediately denies access even when media fails; erasure completion and durable safety checkpoint remain pending until reconciled. Ledger failure causes protected service closure for delivery if current deletion/revocation state cannot be proven. Low disk fails new uploads/jobs safely, never deletes source/audit/last good backup to free space outside policy. Resume writes only after verified backup/ledger readiness.

### 7.3 Safe restore sequence and deterministic outcomes

1. Close browser/API delivery and stop/fence all workers. Restore into an isolated maintenance location, never directly into an open service.
2. Authenticate manifest and key custody, verify full DB/blob/WAL consistency and digests, selected snapshot age/expiry, expected schema/config/policy and monotonic ledger/audit heads. Missing/corrupt referenced evidence withholds READY; do not invent files or accept an incomplete backup silently.
3. Obtain **latest externally custodied** tombstone, revocation, security epoch and protected-effect consumption checkpoint, authenticate continuity and prove it is current. A ledger included only in the old backup is insufficient. Missing/unverifiable latest state keeps service closed.
4. Replay post-snapshot deletion/expiry/revocation and receipt records before any query; purge denied source content and all transitive artifacts, revoke every restored session/reset/capability, reconcile pending once-only actions/outbox. A post-backup consumed effect missing its financial state cannot be auto-reexecuted; hold for authorized reconciliation from its action/effect evidence. Old jobs restart only through fresh authorization/leases.
5. Discard caches/temp/export spools; rebuild protected compatible indexes from authorized live evidence and current manifest. Revalidate active permissions, fingerprints, policy generations and source TTLs; no old index may serve while rebuilding.
6. Check tenant/document/derived denials, representative financial source/bridge integrity, ledger/audit head and backup readiness. Reopen only after all safety checks pass; measure actual RPO/RTO, record any breach, never relabel the target as achieved without evidence.
