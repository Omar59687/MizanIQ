## Operating model and evidence

V0–V3 may progress in synthetic single-operator DEVELOPMENT/DEMO under architecture §2.1–2.2, with unavailable professional/custody/recovery gates explicitly BLOCKED/NOT VERIFIED. Local development acceptance is distinct from full phase acceptance; no failed isolation/authentication/revocation/deletion-safety check permits progression on its affected path. Real financial certification, protected effects and restore reopening stay disabled until the architecture's real-human, method, security-ledger, media, key-custody and review prerequisites are verified. V4 comprehensive coverage and V5 release are not fulfilled by a demo or safe refusals alone.

For each package/phase record in its PR/evidence record: mode; architecture and candidate/base revision or content digest; owned files and requirement/case IDs; fixture/corpus/split/scorer/config hashes; exact commands, environment and test counts; pass/fail/skip counts; subgroup metric denominators and uncertainty; measured hardware/workload/queue-inclusive latency and resource peaks; independent reviewer/custodian identity and scope; open findings, deferred feature coverage, external prerequisites and correction disposition. Use synthetic/publicly licensed evidence only within authorized scope; no sealed gold or secret/raw source payload in ordinary CI logs. Store one concise evidence record per candidate, not architecture versions/review packets. Evidence destinations and executable commands are selected when V0 tooling exists, not fabricated now.

Common proposed development gates: every required deterministic/security case passes; zero observed unauthorized disclosure, bypass, unauthorized/duplicate protected effect, stale-current publication or deletion resurrection; no required test skipped/missing; explicit status on unsupported/missing inputs. These finite-suite criteria are not assurance against every attack. No blanket line-coverage percentage or “95% system accuracy” from averaged component scores. A task's narrower implementation acceptance cannot falsely claim the full phase gate passed.

## Release scorecard — unchanged architecture thresholds

These are proposed statistical release requirements, distinct from the owner-recorded 95% point target and interim DEV floors. Architecture §6 controls the exact population, sampling, rubric, uncertainty and custody; do not round acceptance cutoffs or reweight/remove failures.

| Measure | Observed point target | Proposed release gate |
|---|---|---|
| E2E, 600 answerable tasks, 200/language | ≥95%; every false abstention, timeout, partial/wrong claim/citation/status fails in full denominator | One-sided 95% Wilson L≥.95 overall and each language: ≥579/600 overall and ≥196/200 per language, implying ≥588/600 combined; ≥114/120 each family, ≥36/40 each language×family cell; separate justified abstentions ≥114/120 and ≥38/40 each language; all feature/security/custody/protocol gates |
| Recall@10, separate 1,200 independent queries | Macro ≥95%, fractional query recall, distinct from E2E/all-required-evidence | Macro ≥`.95 + sqrt(ln(20)/2400)` (≈98.533018229%) overall for one-sided 95% Hoeffding L≥.95; macro ≥95% each language, ≥90% each family, security/custody pass; never binomial Wilson on fractional recall |
| Security / finance / completeness | Report actual case/method coverage and errors independently | Any unauthorized content/metadata/effect, stale-current result, deleted/revoked restore delivery or required-feature/custody failure blocks release regardless of accuracy |

No metric here is achieved. A valid completed run below a required bound/floor is NOT ACCEPTED; invalid/missing prerequisites or independence/custody is INCONCLUSIVE/BLOCKED, never green. No independent sealed evaluation is simulated by the single operator.

## CI strategy — specification only, automation starts at V0

No CI workflow is created by this preparation. At authorized V0, implement and verify a runner-neutral local check entrypoint first, then a real PR gate using only an available zero-cost execution route. No Git host/runner/quota is presumed. If hosted checks are unavailable, a separately reviewed local run bound to exact base/candidate plus explicit human/agent review blocks integration until equivalent evidence exists; there is no fabricated hosted green status. Automated branch protection is configured only when supported and authorized; until then integrator enforces these rules manually.

Every future PR must have:

1. **Scope/contract check:** exact base/candidate, phase/mode, owned files, architecture/requirement trace, authorized changes, docs/skill links/frontmatter and no secret/generated/real-data leaks. Check base and candidate test inventories to detect deleted or narrowed required cases. Code/config/model/index/fixture/scorer changes trigger the relevant checks; “docs only” classification must examine the actual diff and requires reviewer agreement.
2. **Genuine build/static checks:** for any application/tooling code, run selected formatter/linter/type checks/build and pinned dependency/license/secret review with actual exit codes. V0 chooses commands against its real toolchain; do not list fictional passing commands or install optional scanners silently.
3. **Required tests:** meaningful unit and real boundary integration tests for the change plus the mandatory security suite and all previous-phase regression suites. Explicitly applicable integration tests cannot be satisfied solely by mocks. Documentation-only PRs run genuine document/skill/reference/scope validation; code suites may be NOT_APPLICABLE only if reviewer verifies no behavioral/config/fixture/scorer changes. This cannot waive phase completion tests.
4. **Measurements when relevant:** actual extraction/OCR cell correctness, financial exactness/status/completeness, retrieval Recall/citation/operand coverage, AR/EN/mixed task correctness/abstention and real local performance with sample counts/config/corpus/hardware; deterministic mock model tests are unit evidence only. Expensive authorized model/OCR/performance runs may execute on the local laptop separately from fast CI, but exact-candidate result artifacts are mandatory before merge if applicable. Missing model/runtime/hardware/authorization is BLOCKED, not silently skipped or “mock accuracy.”
5. **Evidence gate:** required-check inventory declares each case/suite, applicability, minimum collected count and result artifact. Required suite absent, zero tests collected, unexpected skip/xfail, execution error/timeout, missing artifact/scorer/fixture, stale/mismatched revision, or incomplete model measurement fails the aggregate gate. Expected unanswerable/unsupported input tests assert correct denial/status and count as executed tests; they are not skipped tests. Applicability decisions and inventory reductions require independent review before results and cannot waive required safety/regression cases. Never `continue-on-error`, unconditional success, swallowed exit status or a docs-label/path filter that hides required checks; green requires every required entry to pass.
6. **Independent review before merge:** reviewer did not author candidate; bind verdict/findings and evidence to exact content/base, not branch name. No blocking findings, no missing check evidence. Integrator assembles reviewed candidates on a non-main branch, repeats integration/previous-phase regression and gets re-review of new conflicts/behavior; only authorized merge to main follows. An author checking its own work is not this review.

Sealed FINAL (§6 architecture) runs outside developer/agent access and ordinary PR CI under independent custodian; it is required for the relevant final release, not every PR. DEV/validation and mock tests never grant sealed release pass. Gold/questions/scorer must not be uploaded to runner logs or prompt context. Actual final feedback used for tuning retires FINAL. Developer tests validate gate math independently without loading sealed cases.

At V0 verify CI cannot be falsely green by intentionally omitting a required suite, collecting zero cases, failing an integration assertion, skipping a required test, using a stale artifact and making a behavioral change disguised as documentation. Each must fail the real aggregate check. Also verify a genuine complete run passes. These executions are future work; no inert placeholder workflow is permitted now.

## Common correction and integration procedure

On any failure: record requirement/case/candidate and minimal reproduction, mark FAIL/BLOCKED, stop affected integration/release, assign the owning implementer, add or restore a meaningful regression, correct cause, rerun affected metrics and all required prior-phase suites, then obtain independent re-review of resulting content. Never retry nondeterministic failures until green without diagnosis or relax denominators/thresholds after results. If source/method/custody is absent, preserve safe unsupported/denial state and explicit blocker; do not manufacture evidence. Rebase/conflict resolution or relevant config/corpus/model change invalidates affected review/measurements; regenerate them. Changes to accepted product scope require owner direction; technical specialist adjudication cannot be fabricated by an AI reviewer.
